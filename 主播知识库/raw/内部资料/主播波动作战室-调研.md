# 波动不是问题  
分不清哪种波动才是

老板要的是"主播数据稳定"。检索了 20 个可对标系统之后，最关键的发现不在任何一个 AI 产品里，而在 1924 年的休哈特控制图： **波动分两种——过程固有的普通波动，和真正出了事的特殊波动。对普通波动做干预，会让波动变得更大。** 这个系统最值钱的一类输出，是"今天不用管"。

Findings

## 三条决定后面一切的结论

这三条不是观点，是从这个品类已经发生过的成败里读出来的。

### 一、"AI 自动发现异常并解释原因"这个品类，商业上已经失败过一轮

Sisu Data（自动诊断指标变化的关键驱动因子）2023 年 10 月被 Snowflake 收购后**停售独立产品** ；初代 Outlier.ai（每天推送 4–5 条 NLG 洞察）**2022 年解散** ；Anodot 收缩到云成本与电信细分。

同期 Gartner 的数据：BI 平台在企业内平均只有 **29%** 的员工使用，而 99% 的知识工作者认为分析对决策"非常重要"。

**失败原因不是算法不准。** 是"洞察"没有责任人、没有下一步动作、不在任何人每天必经的路径上。这正是我们最需要绕开的坑。

来源：Crunchbase / MarketScreener 收购记录、Outlier.ai 创始团队公开声明、Gartner ABI 采用率

### 二、活下来的系统结构一致：独占数据 + 绕不过的工作流 + 一套贯穿到底的标准

Balto 的表述最准确：**实时辅助 + 自动质检 + 教练 + 洞察，四件事跑在同一套标准上，产生的是复利回报，而不是一次性收益。**

Gong 的护城河今天已经不是"录音"——Zoom、Teams、Meet 都免费录了。真正的差异在**情报层与激活层** ：把对话变成自动化的下一步动作。

映射到我们：**话术标准 = 质检标准 = 教练标准 = 打法库条目，必须是同一份数据。** 四份标准不统一，闭环就是假的。

来源：Balto closed-loop architecture、Observe.AI frontline agents、Gong Revenue AI OS

### 三、"让数据稳定"在方法论上不是异常检测，是统计过程控制

休哈特的核心区分：**普通原因波动** （过程固有，不该动）vs **特殊原因波动** （该查该动）。对普通原因做干预有个专门的名字叫 **tampering** ，戴明的漏斗实验证明它会让波动**变得更大** 。

直播团队最常见的管理失效正是如此：今天掉 18% → 骂主播 → 主播改打法 → 引入新变异 → 下一场波动更大。

**所以这个系统最有价值的一类输出，是"今天不用管，这在正常波动内"。** 所有竞品都不做这件事，而它直接服务于老板"稳定"这个目标。

来源：Shewhart 控制图、Western Electric Rules (1958)、Deming 漏斗实验、Six Sigma DMAIC

Landscape

## 20 个可对标系统

按"它回答了我们哪个问题"分成四类：产品形态、技术内核、工程底座、学习验证。

A

### 闭环运营与教练系统

回答：产品形态长什么样

标杆

#### Gong · Revenue AI OS

多模态收入信号处理 + 专用 agents + 场景化应用。AI Theme Spotter 跨客户找模式，AI Methodology Playbook 识别执行断点，Gong Agents 部署并测量 GTM plays。

**可借鉴：** "发现顶尖销售的策略并自动构建 playbook" —— 就是老板说的蒸馏打法。这条链的产品化范式直接可抄。

标杆

#### Balto / Observe.AI / Level AI

联络中心闭环：实时坐席辅助 + 100% 自动质检 + 教练 + 洞察，四件事共用同一套标准。

**可借鉴（最重要）：** 闭环的定义不是"发现→通知"，而是同一套标准同时驱动辅助、质检、教练和洞察。

标杆

#### Second Nature · AI 对练

AI 买家人格与销售真人对练，即时评分，追踪分数趋势与知识盲区。宣称销售额 +21%，把低绩效者拉到平均线。

**可借鉴：** 打法不能只是发一段文字，要变成**可练习的对练脚本 + 评分卡** 。这是"知道"到"做到"之间唯一的桥。

标杆

#### Salesforce Agentforce · Atlas

四层：Atlas 推理引擎 → Agent Builder → Action Layer → Trust Layer。Agent 五要素：Role / Data / Actions / Guardrails / Channel。

**可借鉴：** 企业级 Agent 的规格书写法。主播 Agent 应按这五要素逐条写死，而不是写一段 prompt。

B

### 异动发现与归因

回答：怎么在噪声里只捞出该管的几件事

工程实践

#### Uber · uVitals + Argos

Metric Cube Creator → Profiler → Seasonality Detector → Rules Engine → **Significance Scorer** → **Publisher（上下文过滤）** → Notifier。Argos 另有 System Health Index 排序异常热点。

**可借鉴：** 显著性打分 + 上下文过滤是对抗告警疲劳的核心零件，不是可选项。没有它，系统第二周就被无视。

开源

#### RiskLoc / Squeeze / HotSpot / Adtributor

shaido987/riskloc 一个仓库实现了全部算法并附基准；NetManAIOps/Squeeze (ISSRE'19)。Adtributor 用 JS 散度按维度排序、以累计解释力停止搜索。

**可借鉴：** 归因要用算法算，不能让 LLM 猜。LLM 只负责把算法结果翻译成人话。**但前提条件我们暂时不满足（见批判 3）。**

反面教材

#### Sisu / Anodot / Outlier.ai

自动诊断指标变化的关键驱动因子，为每个用户建立会随时间改进的个性化模型，每天推送几条 NLG 洞察。

**结局：** Sisu 被收购停售，Outlier.ai 解散。技术都不差，**死在洞察没人负责执行** 。这是我们的头号警戒线。

标杆

#### Databricks Genie / Snowflake Cortex Analyst

YAML 语义视图把业务词映射到表/维度/指标/关系。Databricks 2026-05 研究称新架构把准确率**从 32% 提到 90%+** 。

**可借鉴（关键）：** 决定准确率的是语义层，不是模型。那个 32%→90% 的跃迁来自语义建模。我们必须先建直播指标语义层。

开源

#### WrenAI（Canner）

三服务架构：UI + AI Service（向量检索上下文引导 LLM 产 SQL）+ Engine（MDL 语义引擎）。22+ 数据源，可私有化。

**可借鉴：** 如果要自建语义层，这是现成的参考实现，甚至可以直接用。

开源

#### Anomstack / PyOD / anomaly-agent

Anomstack = Dagster 编排 + pyod + 面板 + 邮件/Slack 告警，并把指标发给 LLM 做二次判断。PyOD 60+ 检测器。

**可借鉴：** MVP 阶段的异常检测直接用现成的，不要自研。省下的时间放到数据标注上。

C

### Agent 工程底座

回答：怎么可靠地跟进到结果

方法论

#### Anthropic《Building Effective Agents》

五种 workflow 模式：prompt chaining / routing / parallelization / orchestrator-workers / evaluator-optimizer。核心原则：简单性、透明性、精心设计 ACI。

**可借鉴：****能用 workflow 就别用 agent，能不用框架就不用框架。** 这条直接否掉了"一上来做大而全的多智能体"。

开源

#### LangGraph

1.0（2025-10）稳定了四项运行时能力：持久化执行、流式、人在回路（interrupt）、记忆管理。状态全在 Postgres，可水平扩展；Saga 补偿模式回滚有副作用的动作。

**可借鉴：** 跟进任务要活 3 天到 2 周，必须靠持久化工作流承载。**但不是第一周该做的事（见批判 5）。**

开源

#### AWS Strands · Agent SOPs

用 Markdown 写的可参数化工作规程，每一步用 **RFC 2119 关键词（MUST / SHOULD / MAY）** 精确控制 agent 行为，既保证可靠执行又保留推理能力。

**可借鉴（重要）：** "蒸馏出来的打法"最好的落地格式就是 SOP 文件 —— 人可读、可评审、可版本管理、机器可执行。比塞进向量库当 RAG 语料强得多。

开源

#### Temporal / Restate / DB-GPT(AWEL)

Temporal journal 每一步，适合跨天重放；Restate 适合 exactly-once 的工具调用；DB-GPT 的 AWEL 是国内私有化友好的工作流表达语言。

**可借鉴：** 第二阶段的编排选型池。第一阶段 cron + Postgres 就够。

D

### 学习与验证

回答：怎么越用越准，而不是越用越乱

开源 / 论文

#### Memp · ExpeL · Reflexion · cass playbook

Memp 把历史轨迹蒸馏成细粒度步骤 + 脚本级抽象；cass 的 Playbook 组件**给每条规则带置信度，并用 evidence gate 先对历史做验证，通过了才允许入库** 。

**可借鉴（关键）：** 打法卡必须带置信度和证据门控。**未经验证的打法不允许下发** —— 这是"沉淀"与"堆垃圾"的唯一区别。

方法论

#### Case-Based Reasoning for LLM Agents

Retrieve → Reuse → Revise → Retain 四步循环，检索相似历史案例并适配当前情况。

**可借鉴：** 天然可解释 ——"上次同样场景这么做有效"，比模型给的抽象理由更容易让主播接受。打法库应按 CBR 结构组织。

开源

#### causalml / CausalLift / GrowthBook

uplift 建模与 CATE 估计；CUPED 降方差、DiD；GrowthBook 开源实验平台。

**可借鉴：** 干预效果必须用因果方法测。"建议后 GMV 涨了 12%"在没有对照的情况下不构成证据（见批判 6）。

方法论

#### SPC / 控制图 / Western Electric Rules / DMAIC

区分普通原因与特殊原因波动。WE 规则四条：超控制限 / 3 中 2 超 2σ / 5 中 4 超 1σ / 连续 8 点同侧。已知权衡：**规则加得越多误报越高** 。

**可借鉴：** 这是"稳定"这个目标的正统方法论，也是本项目最大的差异化来源。

国内基准 / 数据源

#### 生意参谋 / 抖音电商罗盘

生意参谋服务超 3000 万用户，淘天月成交商家 99%+ 在用，做"数据披露 → 诊断 → 分析 → 预测 → 优化"闭环。罗盘分商家/达人视角，六大诊断方向。

**可借鉴：** 国内商家对"诊断"的心智已被教育过，我们的输出要么对齐要么明显超过，不能更差。**也是我们的数据源** ：开放平台近 200 个接口，OAuth 2.0，有频控。

Shortlist

## 从 20 个里选出的前三

选的标准不是"谁最牛"，而是"对我们这个场景，谁回答了一个我们绕不开的问题"。

01

### Balto 式"同一标准闭环" + Gong 式"打法蒸馏"

它回答的是 _产品形态_ 问题 —— 闭环到底长什么样。

关键论断：实时辅助 + 自动质检 + 教练 + 洞察，四件事跑在同一套标准上才产生复利回报，否则只是一次性收益。映射到我们：**话术标准 = 质检标准 = 教练标准 = 打法库条目，必须是同一份数据。**

02

### uVitals 显著性打分 + 多维根因算法 + SPC 控制图

它回答的是 _技术内核_ 问题 —— 怎么在噪声里只捞出该管的那几件事。

三件套分工明确：**SPC 判断"这个波动值不值得管"，多维算法定位"跌在哪个组合上"，显著性打分决定"今天推送哪 5 条"。** 缺任何一件，系统要么吵、要么瞎、要么没人看。

03

### Anthropic workflow patterns + Agent SOP + Memp 证据门控

它回答的是 _工程与学习_ 问题 —— 怎么跟进到结果，并且越用越准。

关键零件：打法以 **SOP 形式落地** （RFC 2119 关键词，人可读可评审、机器可执行），进入打法库前必须过 **evidence gate** 。工程上先用 workflow，不上多智能体。

Red Team

## 专家批判：假设三个月后失败了，复盘会写什么

下面每一条都是在拆上面前三名的假设。看不完的话，至少看第 6 条和第 8 条。

批判 1

### "闭环"这个词最容易骗自己

Balto 的闭环有一个隐含前提：**客服的每一通电话都必须经过它的系统。** 主播不是。主播开播时人在直播间，注意力全在镜头上，**不在你的系统里** 。

你的"闭环"极大概率断在第一环：AI 发消息 → 主播已读不回 → 没有然后了。

修正

闭环的锚点必须是一个主播或中控**无论如何都要走的动作** ——开播前的排品表确认、中控的场次记录、下播后的复盘表提交。把 AI 的输入输出焊死在这个动作上。找不到这样一个动作，就该先去创造它，而不是先写代码。

批判 2

### 你要蒸馏的"优秀打法"，样本本身是脏的

Gong 的蒸馏建立在全样本、结构化、可比的对话语料上。我们的语料来源是：老板的经验（未经验证，且老板是最不可能被系统反驳的人）、外部案例（品类和流量成本完全不同，不可比）、历史高业绩场次（**幸存者偏差 + 与投流严重混淆** ）。

最危险的是第三条：**高 GMV 的场次很可能只是那天千川投得多。** 直接从高业绩场次蒸馏"打法"，等于把运气编码成方法论，然后系统会非常自信地把错误建议下发给全公司 ——**这比没有系统更糟** ，因为它带着数据的权威感。

修正

蒸馏之前必须先做条件控制：同流量档位、同货盘结构、同时段内比较。做不到条件控制，就**只做个人自比，不做跨人推广** 。

批判 3

### 多维根因算法在你的数据规模上会给出高置信度的胡话

Adtributor 系算法的前提是：指标可加、维度基数足够大、有稳定的预测基线。直播场景三条都紧张 —— 一天只有 1–3 场，维度组合极度稀疏（某商品 × 某流量来源 × 某时段常常只有 1 个样本），基线本身还没建起来。

在稀疏数据上跑维度自由搜索，算法**一定会找到一个"解释力很高"的组合** —— 因为组合足够多，总有一个恰好对上。这是多重比较问题，不是算法 bug。

修正

第一阶段退回到更笨但更稳的做法：**固定的指标树公式分解** —— GMV = 观看人数 × 点击率 × 转化率 × 客单价 —— 逐层算贡献度、排序。不做自由维度搜索。样本量到 300 场次以上再上 RiskLoc 那一套。

批判 4

### 控制图要 20–25 个点才能建基线，第一个月的判断统计上不可信

一个主播一天 1–2 场，建一条可信的控制线需要 **2–4 周** 。如果第一周就给老板亮红黄绿灯，你是在用 3 个数据点算标准差。

**信任只能烧一次。** 老板看到系统说"主播 B 异常"，进去发现只是正常波动，第二次他就不看了。

修正

产品必须有"**基线建立中** "这个一等状态，并诚实显示还差多少场次。这个月不是空转 —— 它用来跑数据接入、标注历史场次、建立沟通习惯。另外 Western Electric 规则本身也有已知权衡：**规则加得越多误报率越高，不要八条全开。**

批判 5

### 第一周把预算花在 LangGraph 架构上是典型的过度工程

Anthropic 自己的原则写得很清楚：**能用 workflow 就别用 agent，能不用框架就不用框架。**

你们的真实瓶颈不是编排，是**数据接入和标注** 。持久化执行、Saga 补偿、checkpointer —— 这些在你有 500 个待跟进任务时才是问题，在你有 8 个主播时不是。

修正

MVP 用 cron + Postgres + 每天一次 LLM 调用 就能跑通闭环。省下的两周用来**把最近 50–100 场直播打上结构化标签** （主播、时段、货盘顺序、投流预算、脚本版本、异常事件）。那批标注数据才是护城河 —— 架构随时可以重写，历史标注补不回来。

批判 6

### "AI 建议后 GMV 提升 12%" 几乎必然是均值回归，不是效果

这是这类系统最经典的自欺，而且极难自己发现。机制很简单：**你恰恰是在数据异常低的时候去干预的。即使什么都不做，下一场也会向均值反弹。** 于是每一次干预看起来都"有效"。

更糟的是这个假信号会反向污染打法库：无效打法因为"验证有效"而晋级为公司标准，然后被推广到全体主播。

修正 · 按可行性排序

**① 场次内分段随机（最推荐）** ：前 30 分钟用新话术、后 30 分钟用旧的。直播天然有分段结构，这是几乎免费的随机化单元。**② holdout 组** ：检测到异常但故意不干预的 5–10%，统计最干净但老板通常不接受。**③ 个人基线预测残差** ：预注册"不干预预计多少"再比。**④ 前后对比：单独使用等于没测。**

批判 7

### 老板要的是"AI 管主播"，主播感受到的是"AI 监工"

公开数据很清楚：**85%** 的一线员工认为用 AI 替代人是"巨大错误"，**64%** 担心 AI 抢走工作；一线员工对 AI 的乐观比例是 **39%** ，知识工作者是 53%。而组织内的 AI 落地通常是高层决定、向下通知，员工被告知而非被咨询。

主播的反制能力极强而成本极低：挂机刷停留、故意压低前 30 分钟把基线做低、把话术做成"给系统看的表演"。**指标一旦挂钩考核就会被 Goodhart 定律吃掉 —— 而这恰好会增大波动，与项目目标完全相反。**

修正 · 第一版必须写死

AI **不参与考核扣钱** 并对全员公示；诊断只对主播本人与直属主管可见，**不做横向排名榜** ；**只与主播自己的基线比** ；建议**必须可反驳** ，反驳直接写入打法卡的"适用条件"字段；老板端看"问题 + AI 动作 + 结果"，不看主播排行榜。

批判 8

### 最该先做的一件事，不在任何一个方案里

**"让主播数据稳定"可能不是一个真问题。**

直播场次 GMV 的方差，绝大部分可能来自平台流量分配和投流预算，主播只能解释其中一部分。**如果主播相关的残差方差只占 15%，这个项目的天花板从第一天起就锁死在 15%** ，做三个月也只能拿到其中一小部分。
    
    
    # 项目的第一件事，不是写 PRD，是这个：
    Var(场次 GMV) = **流量贡献** + **投流预算贡献** + **货盘/商品贡献**
                  + **时段贡献** + 主播残差 + 噪声
    
    # 有 50 场历史数据就能跑一个粗版，一天做得完。
    # 如果发现"货盘"才是最大方差来源 —— 第一个 Agent 应该做选品，不是主播。

修正

方差分解必须在动手写系统之前完成，**并且结论要原样告诉老板 —— 包括结论对项目不利的情况。** 这一天的产出决定这个项目值不值得做、以及应该先打哪一块。

Options

## 三套方案，请选一套

不是简版 / 中版 / 豪华版，而是三种不同的战略下注：赌"判断准"、赌"证明有效"、还是赌"主播愿意用"。三者最终都会长成完整系统，但第一个月做什么、第一个月拿什么给老板看，完全不同。

方案 A · 赌判断准

### 主播稳定性控制塔

给每个主播建一条统计意义上的正常线，只在真正越线时才出手。系统最有价值的输出是"今天不用管"。

北极星**在控率** —— 场次表现落在个人控制限内的比例。GMV 涨了可能是投流涨了，**在控率涨了只可能是管理变好了** 。

内核个人控制图 → WE 规则（只开 2–3 条）→ 普通原因则明确输出"无需干预"；特殊原因才触发指标树分解 → 动作卡 → 主管审批 → 下一场回看

技术Anomstack/PyOD + 自写 SPC（<300 行）；只做公式分解不做多维搜索；cron + Postgres；LLM 只负责翻译成人话

节奏第 2 周有东西看 · **第 6 周有第一组可信数据**

最大风险老板嫌"AI 说不用管"没价值，看不到 AI 在干活。需要提前对齐：**不制造噪声本身就是产出** 。另需核对场次密度（主播 ≥ 6 人、每周 ≥ 4 场），否则控制限永远建不可靠。

什么时候选它老板的原话就是"稳定"，你想最直接地回应他；团队人少，要 6 周内拿出可信结果。

方案 B · 赌能证明

### 归因–干预–验证引擎

把每一次干预都变成一次登记在册的实验，用因果方法证明哪些打法真的有用，让打法库带着置信度成长。

北极星**已验证打法数量** （过了 evidence gate 的打法卡）与**打法命中率** 。这是三个方案里唯一能真正回答"这套东西到底有没有用"的。

内核检测 → 指标树分解 → CBR 检索相似案例 → 生成方案 → **预注册实验** → 场次内分段随机 → 效果测量 → **Evidence Gate** → 打法卡状态机（候选→试验中→已验证→已淘汰）

技术GrowthBook / 自建分流 + causalml (CATE)；打法库用结构化 YAML（Agent SOP 风格 + RFC2119），不是向量库；跨天跟进需要持久化工作流

节奏第 4 周有东西看 · **第 8 周出第一份置信度报告**

最大风险**老板等不了 8 周 —— 这是最可能的死因。** 其次是纪律：一旦中途"这次就先不预注册了"，整套机制立刻作废。主播也可能不配合分段随机。

什么时候选它老板能接受两个月看结果，且真在意"有没有用"而不是"看起来在动"；你想做的是一个未来能卖给同行的**产品** ，不只是内部工具。

方案 C · 赌有人用

### 主播 Copilot + 打法知识库

先做主播每天真的会用的那个助手 —— 开播前给脚本和排品建议，下播后陪他复盘，记得他说过的每一句话。

北极星**周活跃复盘率** 与 **建议采纳率** 。配套：主播反馈条数 —— **反驳也算，反驳是最有价值的数据** 。

内核飞书/企微里的主播助理，一人一档案。开播前 3 条准备事项 → 下播后 30 分钟主动发起复盘对话（**这是焊死的必经动作** ）→ 主播可反驳 → 反驳写入打法卡适用条件 → 经营档案自动更新

技术飞书自建应用 / 企微机器人（webhook + 事件订阅）；档案用 Postgres 结构化存储；检测先用简化版（个人均值 ±1.5σ）

节奏**第 2 周主播就能用上** · 第 3 周老板能看到主播在和 AI 对话 —— **感知最快**

最大风险**最经典的死法：体验很好但没用。** 底层判断不准 → 主播三天就发现建议是套话 → 静默流失，**而且第二次很难请回来** 。还要小心变成"AI 监工"的观感（见批判 7）。

什么时候选它老板最在意"和主播沟通"这个原话，需要尽快让他看到东西；你担心做完系统没人用。

---|---|---|---  
**赌什么**|  判断准| 能证明| 有人用  
**北极星**|  在控率| 已验证打法数| 复盘率 / 采纳率

## 我的建议

**先选 A，第 3 周把 C 的交互层叠上去，第 6 周把 B 的验证机制叠上去。**

  1. A 直接回应老板原话（稳定），且是唯一门槛低到 **6 周能拿出可信数据** 的路径。
  2. A 的基线层是 B 和 C 的共同前提 —— **没有可信基线，B 无法测效果，C 说不出人话。**
  3. C 单独先做的风险最大：判断不准的 Copilot 会**一次性烧掉主播的信任** ，而且很难请回来。
  4. B 的护城河最深，但它必须建在 A 的基线和 C 的执行通道之上。

**如果必须只选一个，选 A。**  
**如果老板下周就要看到"AI 在和主播说话"，选 C** —— 但要接受第一版会说套话，并提前和老板对齐这一点。 

**无论选哪套，第 0 周都是同一件事：跑一次方差分解** （批判 8）。用历史场次数据算出 GMV 方差里主播残差占多少。这一天的产出决定项目的天花板，也可能推翻上面全部三套方案 —— 那也是有价值的结论。
